This repo is an autograder written in shell. It covers the loop a university assignment system needs: create an assignment, take submissions, summarize them, run tests, and produce a mark.

The constraint shapes the design. All state lives in the filesystem, and dash is the only language available.

## Assignment and Submission Flow

The add script checks the assignment name, the solution file, the autotest spec, and the automarking spec before it writes anything. What passes goes under a hidden project directory.

The submit script checks that the assignment exists, that the student zID is in the expected format, and that the submitted file is there. It then creates a folder per student and records the timestamp and file size.

## Marking Flow

The marking script reads the automarking spec and runs the student's latest submission against the reference solution. It captures stdout, stderr, and the exit status separately, then compares.

Comparison has switches for blank lines, case, digits, and whitespace. They matter because byte-for-byte equality is the wrong test for most student output: a trailing newline or a capitalized word is rarely what the assignment was asking for.

## Design Constraints

Dash keeps the code close to POSIX. That shows up in the places that are easy to get wrong: quoting, path validation, exit codes, and temporary output files. An unquoted variable is one space away from a broken path.

## Knowledge Points

- Shell can model a real system when the data already looks like files and folders.
- Every CLI argument is a potential path or command input, so validation is not optional.
- An autograder has to keep stdout, stderr, and exit status apart. Merging them loses the difference between wrong output and a crash.
- Diff options make marking fairer for differences that do not matter.
- File-backed state is easy to inspect. It stays that way only with consistent naming and cleanup rules.
- POSIX shell pushes toward small commands and explicit control flow.
- A CLI should fail loudly and consistently when inputs are malformed.

## Takeaway

Most of the behavior here comes from the directory layout and the exit codes, not from a framework. Writing it in dash made the boundaries obvious, because nothing else was validating for me.

这个仓库用 shell 写了一个自动评分器，覆盖大学作业系统的完整流程：建作业、收提交、汇总提交、跑测试、算分。

限制条件决定了它的写法：所有状态都放在文件系统里，能用的语言只有 dash。

## 作业和提交流程

添加脚本先校验作业名、标准答案、自动测试规范和评分规范，都通过以后才写进隐藏的项目目录。

提交脚本校验作业是否存在、学生 zID 的格式、提交的文件是否齐全，然后给每个学生建目录，记下时间戳和文件大小。

## 评分流程

评分脚本读取评分规范，拿学生最新一次提交去跑参考答案，分别捕获 stdout、stderr 和退出码，再做比较。

比较支持忽略空行、大小写、数字和空白字符的开关。这些开关有实际作用。学生输出很难做到逐字节一致，多一个换行、首字母大写，通常跟作业要考的内容无关。

## 设计约束

用 dash 写的代码贴近 POSIX，代价是引用、路径校验、退出码和临时文件这些地方都要格外小心。变量忘了加引号，路径里多一个空格就会出错。

## 知识点

- 数据本来就能映射成文件和目录时，shell 也能撑起一套真实系统。
- CLI 的每个参数都可能变成路径或命令输入，校验不能省。
- 自动评分器要分开保存 stdout、stderr 和退出状态，混在一起就分不清"输出错"和"程序崩了"。
- 忽略格式差异的比对选项，能让评分对无害的排版差异更公平。
- 文件状态看得很清楚，但前提是命名和清理规则统一。
- POSIX shell 会推着你写小命令和显式控制流。
- 输入不合法时，CLI 应该明确、稳定地报错。

## 总结

这里大部分行为来自目录结构和退出码，跟框架没什么关系。用 dash 写反而把边界暴露出来：没有任何一层在替我兜底做校验。
