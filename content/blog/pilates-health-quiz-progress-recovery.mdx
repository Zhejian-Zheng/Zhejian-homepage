The Pilates Health Quiz started as a small project. The goal was to let someone answer a step-by-step health questionnaire, keep the answers on the backend, and produce a basic health assessment at the end. On the surface it is a simple form. Most of the work went into saving each step, restoring progress when someone comes back, validating answers on the server, recognizing the session, and handling the case where a person closes the page halfway through.

## Project background

The workflow is easy to describe. A user fills in gender, goals, age, height, current weight, target weight, and exercise frequency, one step at a time. After each step, the frontend syncs the current answer to the backend. If the user closes the page and returns later, the app should restore the previous answers and the step they were on.

The stack:

- Next.js 16
- React 19
- Prisma
- PostgreSQL / Supabase
- Zod
- Vitest

## Saving each step

It is tempting to build the questionnaire as one final submission. This project needed every step saved, so someone who leaves midway does not lose progress.

The frontend saves whenever the user selects an answer or submits a numeric input:

```ts
PATCH /api/sessions/:sessionId/answers
```

The request body carries only the increment for the current step:

```ts
{
  currentStep: nextStep,
  answers: [
    {
      stepKey: question.key,
      questionKey: question.key,
      value
    }
  ]
}
```

On the backend, Prisma `upsert` writes the answer. Changing the same question updates the existing row instead of creating a duplicate.

## Progress recovery: from localStorage to a cookie session

The first version generated a random `sessionId` and stored it in frontend `localStorage`. It worked, with one obvious limitation: session identity depended entirely on data the frontend could read. That is not a server session.

So I moved the session into an HttpOnly cookie.

The flow now:

1. The first answer triggers `POST /api/sessions`.
2. The backend creates the user and the assessment record.
3. It writes an HttpOnly cookie named `pilates_health_quiz_session`.
4. When the user reopens the page, the frontend calls:

```ts
GET /api/sessions/current
```

The backend reads the sessionId from the cookie and returns that user's assessment progress and saved answers.

The frontend no longer reads or writes a local random ID. Session recognition happens on the backend, which is closer to how login and session handling work in a real product.

## The 409 that blocked edits

I hit a bug that seems typical of step-by-step flows. When a user went back to an earlier question and changed the answer, the backend returned `409 Conflict` and the frontend showed "Unable to save your answer."

The backend validated progress and refused to let `currentStep` move backward. Editing an earlier question sends a `currentStep` lower than the furthest step already recorded.

The fix separated the step the UI is on from the furthest step the backend knows:

- The UI can go back to earlier questions and edit them.
- When saving, `currentStep` is never lower than the backend's known maximum.

The backend keeps its anti-skip validation, and users can still fix old answers.

## Validation on the backend

The project does not rely on frontend restrictions alone. The backend uses Zod and some custom checks:

- Height must be between 100 and 250 cm.
- Weight must be between 30 and 300 kg.
- Age must be between 13 and 100.
- Question keys must match known steps.
- Required prerequisite steps cannot be skipped.

So a request that skips the frontend and posts invalid data straight to the API still fails.

## Tests

I wrote tests for the main API flows:

- Creating a session.
- Saving answers step by step.
- Blocking skipped-step submissions.
- Blocking invalid answers.
- Restricting access to unpaid results.
- Unlocking full results after payment.
- Restoring current progress through the cookie session.

The cookie test checks that `Set-Cookie` is present, sends that cookie to `/api/sessions/current`, and confirms that the backend restores the right session and answers.

## Where the project stands

The project has the core skeleton of a health assessment product:

- Step-by-step questionnaire flow
- Incremental saving at each step
- Backend persistence
- Cookie session progress recovery
- Backend field validation
- A simulated payment unlock
- API test coverage

The next step is turning the guest cookie session into a real account system: email login, OAuth, or binding the cookie session to an account. That would let someone recover progress on another device.

## What I took away

A questionnaire stops being a form once it has to behave like a product. The decisions that matter are about state: where it is saved, how it is restored, where validation lives, how it is protected, and what happens when things go wrong.

Moving the session from a local random ID to an HttpOnly cookie made the app feel closer to a real product. Session recognition no longer depends on a value the frontend can read. The backend owns it now, which is the beginning of real session handling.

前段时间做了个小项目，叫 Pilates Health Quiz。目标不复杂：让用户按步骤填一份健康问卷，答案存在后端，最终生成一份基础健康评估。表面上它就是个表单，真正花时间的都在后面：每一步怎么存、用户回来怎么恢复、答案在哪一层校验、session 怎么认，以及用户中途关掉页面之后怎么办。

## 项目背景

流程一句话能说完：用户依次填性别、目标、年龄、身高、当前体重、目标体重、运动频率，每完成一步，前端就把这一步的答案同步到后端。用户关掉页面再进来，系统要能还原之前填过的内容和当前步骤。

技术栈：

- Next.js 16
- React 19
- Prisma
- PostgreSQL / Supabase
- Zod
- Vitest

## 每一步都保存

最容易想到的写法是一次性提交。这个项目要求每一步都落库，用户中途退出才不会丢掉已经填的内容。

用户选中一个答案，或者提交一个数字，前端就调一次保存接口：

```ts
PATCH /api/sessions/:sessionId/answers
```

请求体只带当前这一步的增量：

```ts
{
  currentStep: nextStep,
  answers: [
    {
      stepKey: question.key,
      questionKey: question.key,
      value
    }
  ]
}
```

后端用 Prisma 的 `upsert` 写答案。同一道题改答案时会更新已有记录，不会多出一条。

## 进度恢复：从 localStorage 到 Cookie Session

最早的做法是在前端生成一个随机 `sessionId`，存进 `localStorage`。能用，但问题也很直接：session 的身份完全来自前端能读到的一个值，这和真正的后端 session 不是一回事。

后来我把它换成了 HttpOnly cookie session。

现在的流程：

1. 用户第一次答题，前端请求 `POST /api/sessions`
2. 后端创建用户和测评记录
3. 后端写入 HttpOnly cookie：`pilates_health_quiz_session`
4. 用户再打开页面时，前端请求：

```ts
GET /api/sessions/current
```

后端从 cookie 里取出 sessionId，返回这个用户的测评进度和已保存的答案。

这样前端不用再碰本地随机 ID，session 识别由后端负责，和真实产品里的登录态更接近。

## 踩过的坑：409 保存冲突

开发时遇到过一个很典型的问题。用户回到前面的题改答案，后端返回 `409 Conflict`，前端提示“无法保存你的答案”。

原因是后端有进度校验，不允许 `currentStep` 倒退。用户编辑前面的题时，前端发过去的 `currentStep` 可能比后端记录的最远进度小。

改法是把“UI 当前在第几步”和“后端已知走到第几步”分开：

- UI 可以自由回到前面的题修改。
- 保存时，`currentStep` 不低于后端已知的最高进度。

后端的防跳步校验还在，用户也能改旧答案。

## 后端也得校验

这个项目没有只靠前端限制输入。后端用 Zod 和自定义校验兜底，比如：

- 身高必须在 100-250 cm
- 体重必须在 30-300 kg
- 年龄必须在 13-100
- 问题 key 必须是已知步骤
- 不能跳过前置必填步骤

即使用户绕过前端直接调 API，非法数据也进不来。

## 测试

核心 API 流程都加了测试：

- 创建 session
- 分步保存答案
- 阻止跳步提交
- 阻止非法答案
- 未付费结果的访问限制
- 支付后解锁完整结果
- 用 cookie session 恢复当前进度

cookie session 那条测试会先确认响应里有 `Set-Cookie`，再拿这个 cookie 请求 `/api/sessions/current`，检查后端恢复出来的 session 和答案对不对。

## 现在做到哪一步

项目现在已经有了一个健康测评产品的基本骨架：

- 分步问卷
- 每步增量保存
- 后端持久化
- Cookie session 恢复进度
- 后端字段校验
- 支付解锁结果的模拟流程
- API 测试覆盖

接下来比较明确的一步，是把游客 cookie session 换成真正的账户体系：邮箱登录、OAuth 登录，或者把 cookie session 绑到用户账户上。这样用户换设备也能接着填。

## 复盘

问卷一旦要当产品用，就不只是表单了。真正要定的是状态：存哪、怎么恢复、校验放哪一层、出错的时候怎么处理。

从本地随机 ID 换成 HttpOnly cookie session 之后，session 由后端识别，不再依赖前端那个随机值。应用因此更像线上产品，用户会话也开始由后端管了。
