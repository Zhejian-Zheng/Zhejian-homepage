Repo License Info is a set of notes I keep on open-source licenses. It covers MIT, Apache, GPL, LGPL, AGPL, BSD, MPL, EPL, Unlicense, and CC0, and it focuses on the differences that change how a project can be used.

A license is a design choice. It sets what other people may do with the code: use it, modify it, redistribute it, ship it inside their own product.

## License Families

MIT, BSD, and Apache are permissive. When the goal is broad reuse, they are the easy choice: attribution is usually required, and the code can end up inside a closed-source product.

GPL is copyleft. A derivative work has to carry similar freedoms. AGPL extends that requirement to software people reach over a network instead of installing.

CC0 and Unlicense try to remove the restrictions altogether. What that means in practice depends on the jurisdiction, so I would not assume the two behave the same everywhere.

## Practical Considerations

The right license depends on what the project is for. A portfolio demo, a library other people import, a commercial tool, and a collaborative research project can want very different terms.

I use the repo to compare clauses before I pick a license. For production or company work, I would read the original license text again rather than act on notes like these.

## Knowledge Points

- A repo with no license is not automatically free for others to reuse.
- Permissive licenses lower the cost of adoption and integration.
- Copyleft licenses keep derivative works open.
- Apache 2.0 carries explicit patent language, which is the part companies tend to care about.
- AGPL matters when the software is delivered mainly as a network service.
- License compatibility decides whether two dependencies can sit in the same project.
- A notes repo should say plainly that it is not legal advice.

## Takeaway

License choice sits half in engineering and half in law. The code is technical; reuse is not.

Repo License Info 是我整理的一份开源许可证笔记，覆盖 MIT、Apache、GPL、LGPL、AGPL、BSD、MPL、EPL、Unlicense 和 CC0，重点放在真正影响项目使用方式的差异上。

许可证是设计决策。它规定了别人能拿这份代码做什么：使用、修改、再发布，或者集成进自己的产品。

## 许可证家族

MIT、BSD 和 Apache 属于宽松型。想让代码被广泛复用时，这类许可证最省事：一般要保留署名，但允许代码进入闭源产品。

GPL 是著佐权许可证，衍生作品必须保留类似的自由。AGPL 把这套要求延伸到通过网络使用软件的场景，用户不一定要把程序装到本地。

CC0 和 Unlicense 想把限制降到最低。实际效果跟司法管辖区有关，不能默认这两者在哪儿都一样。

## 实际考量

选哪个许可证，取决于项目要做什么。作品集演示、别人会当依赖引入的库、商业工具、协作研究项目，需要的条款可以完全不同。

这份笔记我拿来对比条款。真要上生产、或者涉及公司项目，我会把原始条款再读一遍，而不是照着笔记直接定。

## 知识点

- 仓库没有许可证，不代表别人可以随便复用。
- 宽松型许可证降低采用和集成的门槛。
- 著佐权许可证让衍生作品保持开放。
- Apache 2.0 有明确的专利条款，企业选许可证时通常最在意这一条。
- 软件主要以网络服务形式交付时，AGPL 就适用了。
- 许可证兼容性决定两个依赖能不能放进同一个项目。
- 笔记仓库要写清楚：这里是学习记录，不是法律意见。

## 总结

许可证这个题目，一半在工程，一半在法律。代码是技术的，复用不是。
