A chat interface makes device automation approachable, but a message is not always a request to operate a phone. Sidecar's conversation service separates the two cases explicitly. This review is based on the local working tree as of November 5, 2026, at `9a28e63` with uncommitted changes. The links below point at that baseline. This note does not report a new end-to-end acceptance run.

## Classify before creating work

`conversation.py` defines four decision kinds: reply, clarify, time, and device. A capability question can receive an ordinary answer. An ambiguous app request can ask for clarification. Time queries use the server clock with a validated timezone instead of creating a device job.

The same service backs both the web entry and the OpenAI-compatible chat entry. With the routing in one place, two interfaces are less likely to give the same sentence different operational meanings.

## The connection is not the task

According to the README, the server starts an independent worker and persists the queue in SQLite. Closing the browser or ending a chat stream does not cancel the task. The host and device still need to stay online.

A client should keep the task ID and render its status separately from the chat transport. A response timeout only means the client stopped waiting; it does not establish that device execution stopped.

## Retrying is different from asking again

The compatibility interface persists request deduplication across restarts. Retrying the same request can reuse the task. Deliberately repeating the goal needs a new conversation turn or a fresh idempotency key. Reusing a key for a different request is invalid.

This boundary keeps transport retries from silently becoming duplicate device actions. It does not promise exactly-once effects in a third-party app.

## Make handoff visible

The interface needs to show whether a task is queued, active, paused, or waiting for a person, along with its latest observation. A generic "continue" button must not be read as permission to send a prepared email.

My takeaway is to design the task lifecycle before polishing the chat bubble. Conversation makes intent easier to express; durable task state makes execution easier to inspect.

聊天界面让设备自动化更容易上手，但一条消息不一定就是“操作手机”的请求。Sidecar 的对话服务把这两种情况明确分开。这篇笔记看的是 2026 年 11 月 5 日的本地工作区，基线为 `9a28e63`，另有尚未提交的修改。文末链接指向该基线；这篇笔记没有新的端到端验收结果。

## 先分类，再创建工作

`conversation.py` 定义 reply、clarify、time、device 四种决策。问它能做什么，可以直接用一句话回答；App 指代不明，可以要求澄清；时间查询用服务端时钟加校验过的时区，不会创建手机任务。

网页入口和 OpenAI 兼容聊天入口共用这个服务。路由集中在一处，两个界面就不容易对同一句话给出不同的操作含义。

## 连接不等于任务

README 说明服务会启动独立 worker，并把队列持久化到 SQLite。关掉网页或结束聊天流不会取消任务，但宿主机和设备仍需在线。

客户端要保留任务编号，把任务状态和聊天连接分开显示。请求超时只说明客户端不再等待，不能说明设备停止执行。

## 重试与再次提出请求不同

兼容接口的请求去重记录可以跨重启保留。重试同一个请求可以复用任务；主动再执行同一目标，需要新的对话轮次或新的幂等键。不同请求不能复用同一个键。

这条边界避免传输层重试悄悄变成重复的设备动作，但不承诺第三方 App 里的副作用具备 exactly-once 保证。

## 让交接状态可见

界面要显示任务处于排队、执行中、暂停，还是等待人工处理，同时给出最近一次观察。一个笼统的“继续”按钮，不能被理解成授权发送已经写好的邮件。

我的体会是，先设计任务生命周期，再打磨聊天气泡。对话让意图更容易表达，持久化的任务状态让执行更容易检查。
