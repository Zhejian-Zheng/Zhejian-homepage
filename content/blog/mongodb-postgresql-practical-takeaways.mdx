Working with both databases changed the question I ask first. These days it is what shape the data has, and how often I expect that shape to change.

PostgreSQL fits when the data has a clear structure and the relationships between records carry weight. MongoDB fits when the shape moves every few releases, or when a record naturally holds nested information that would be awkward to spread across tables.

## PostgreSQL

PostgreSQL is a relational database: tables, rows, columns. It is at its best when the system needs relationships, constraints, joins, and transactions.

I reach for it for core application data: users, orders, payments, permissions, project records. Anything where a wrong value is expensive to fix belongs there. SQL is the other reason I stay with it. Reporting, aggregation, and debugging are a query away.

## MongoDB

MongoDB is a document database. Related fields live together in one document, which is convenient when the application data already looks like a nested object.

I use it for task records, logs, user preferences, AI workflow metadata, scraped data, and prototypes whose fields are still moving. The schema is allowed to change, and a new field does not need a migration first.

## Tradeoffs

Flexibility costs something. MongoDB is quick to start with, and without discipline the collections drift. The same field shows up in several shapes, and every reader has to work out which one it got.

PostgreSQL asks for more schema design up front. That work tends to pay back once the project grows.

## Knowledge Points

- PostgreSQL handles structured relational data and strong consistency better.
- MongoDB is the easier place for document-style data whose schema is still moving.
- SQL makes complex queries, joins, and reports something I can reason about directly.
- Documents save work when the data is nested and would not need many joins.
- The right choice follows the data shape and the product requirements, not a ranking.

## Takeaway

My default is PostgreSQL for important relational data and MongoDB for flexible document-style data.

A full-stack system can run both: PostgreSQL for the stable core, MongoDB for dynamic records, logs, and workflow state.

The rule I use now: PostgreSQL for data I need to trust, MongoDB for data whose shape I am still working out.

用过 MongoDB 和 PostgreSQL 之后，我挑数据库时先问的问题变了：数据是什么形状，这个形状多久会变一次。

PostgreSQL 适合结构清晰、记录之间关系重要的数据。MongoDB 适合字段经常变动的情况，也适合一条记录本身就是嵌套结构、拆成多张表反而别扭的数据。

## PostgreSQL

PostgreSQL 是关系型数据库，数据放在表、行、列里。系统需要关联关系、约束、join 和事务时，它最合适。

核心业务数据我基本都放在这里：用户、订单、支付、权限、项目记录。写错一次要花时间修的地方，都算这一类。SQL 是另一个原因，报表、聚合、查问题，一条查询就能说清楚。

## MongoDB

MongoDB 是文档数据库，相关字段存在同一个文档里。应用数据本来就是嵌套对象时，这种存法很顺手。

任务记录、日志、用户偏好、AI 工作流元数据、爬取数据，以及字段还在变的原型，我会用 MongoDB。schema 可以改，加一个字段不用先写迁移，迭代就快得起来。

## 权衡

灵活性有代价。MongoDB 起步快，但如果没人管，集合里的字段会慢慢长出好几种形态，读数据的人得先判断自己拿到的是哪一种。

PostgreSQL 前期要在 schema 上多花时间。项目长大以后，这部分投入通常会还回来。

## 知识点

- 结构化的关系型数据，或者需要强一致的场景，PostgreSQL 处理得更好。
- 文档型数据、schema 还在动的时候，MongoDB 更合适。
- SQL 让复杂查询、join 和报表可以直接推理。
- 数据本身是嵌套结构、又不需要大量 join 时，用文档存更省事。
- 选哪个数据库，取决于数据形态和产品需求，跟排名无关。

## 总结

我现在的默认做法是：重要的关系型数据交给 PostgreSQL，文档型数据交给 MongoDB。

全栈系统里两者可以同时跑：PostgreSQL 管稳定的核心，MongoDB 存动态记录、日志和工作流状态。

这套分工我用下来是成立的：需要信得过的数据放 PostgreSQL，形状还在变的数据放 MongoDB。
