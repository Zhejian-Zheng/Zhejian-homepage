<ArticleLanguage language="en">

Reviewing a GitHub repository is an engineering investigation. Before making any judgment, a reviewer needs to understand the project boundary, runtime model, dependency graph, testing surface, and the paths where bugs would actually hurt users.

A review agent should be built around that process: a code-aware system that clones or inspects a repository, builds a project map, runs local verification, and ties every finding to a file, a command, and a failure mode. A generic chatbot commenting on isolated snippets does not get you there.

## System Goals

The agent has three goals:

- Build a structured understanding of the repository.
- Detect high-signal engineering risks.
- Produce findings a maintainer can act on immediately.

Correctness, security, maintainability, and test gaps come before style preferences. A good agent should be able to say: this request path accepts user input, passes it into this parser, writes to this storage layer, and currently has no test covering malformed input.

## Architecture

The review agent is a pipeline:

```text
GitHub Repository
      |
      v
Repository Loader
      |
      v
Project Indexer
      |
      v
Static Analysis + Semantic Search
      |
      v
Test / Build / Lint Executor
      |
      v
Risk Scoring Engine
      |
      v
Review Report Generator
```

Each stage owns one responsibility. Keeping them separate makes the agent easier to debug, measure, and improve.

## Repository Loading

The first step is to load the repository in a reproducible way. The agent needs to capture:

- GitHub URL, branch, commit SHA, and pull request number if available.
- Language and framework signals from files like `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml`, or `build.gradle`.
- CI configuration from `.github/workflows`, `circleci`, `buildkite`, or similar directories.
- Dependency lockfiles such as `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `poetry.lock`, `uv.lock`, or `Cargo.lock`.

The commit SHA matters because the review has to be reproducible. If a finding points at a moving branch instead of a commit, the evidence can drift.

## Project Indexing

Once the repository is available locally, the agent builds a project index with both structural and semantic data:

- File tree, with generated artifacts and build output excluded.
- Entry points: API routes, CLI commands, app bootstraps, workers, scheduled jobs.
- Exported functions, classes, interfaces, and modules.
- Dependency edges between files.
- Test files mapped to implementation files.
- Configuration files and environment variable usage.

For small repositories, filesystem traversal and language-aware parsers may be enough. Larger codebases need a hybrid index:

- Fast lexical search with tools like `ripgrep`.
- AST parsing where a parser exists for the language.
- Embedding-based retrieval for semantic questions.
- Call graph or import graph extraction for dependency reasoning.

The agent does not need to read every file into the model context. It can retrieve files based on the current review hypothesis.

## Static Analysis Layer

The static analysis layer looks for patterns that deserve human attention. Examples:

- User input reaching filesystem, SQL, shell, network, or deserialization APIs.
- Authentication or authorization checks that are missing or inconsistent.
- Broad `catch` blocks that hide operational failures.
- Unsafe shell command construction.
- Missing request size limits.
- Update flows prone to races.
- Shared mutable state in concurrent code.
- Unbounded retries, pagination, recursion, or queue processing.
- Secrets accidentally committed into source.
- Error paths without tests.

This layer should combine deterministic rules with LLM reasoning. Rules handle exact patterns; an LLM can connect several files into one behavioral path.

## Verification Execution

A review agent becomes much more useful when it can run the commands a maintainer would run:

```bash
npm test
npm run lint
npm run typecheck
pytest
go test ./...
cargo test
```

The agent should infer commands from package scripts, CI workflows, and README instructions. For each run it should record the command, exit code, runtime, the failure output that matters, and whether the failure looks related to the reviewed change.

A finding that was never run is weaker evidence. Commands that fail for missing services or credentials still belong in the report.

## Risk Scoring

Not every issue deserves the same attention. A practical agent scores findings by risk:

```text
risk = impact * likelihood * reachability * confidence
```

- Impact measures how bad the failure would be.
- Likelihood measures how likely the failure is in normal usage.
- Reachability measures whether the code path is exposed to real users or automation.
- Confidence measures how much evidence the agent has.

Scoring keeps the review from turning into a long list of low-value comments. The list should start with issues that could cause data loss, security exposure, production outages, broken releases, or major regressions.

## Review Output

A useful finding is short, specific, and tied to evidence:

```text
Severity: High
File: src/api/import.ts
Issue: Uploaded files are parsed before size and content-type validation.
Why it matters: Large or malformed files can cause excessive memory usage before rejection.
Suggested fix: Validate request size and MIME type before reading the full body.
Verification: Add tests for oversized files, unsupported MIME types, and malformed payloads.
Evidence: The import route calls parseUpload(body) before validateUploadMetadata(req).
```

Vague advice like "improve validation" gives a maintainer nothing to check. The format above names the failure mode instead.

## GitHub Integration

Two integration modes are common:

- Pull request review mode: the agent reviews the diff, then expands into surrounding files when needed.
- Repository audit mode: the agent reviews the whole repository and produces an architecture and risk report.

For pull requests, scope control matters. The agent should focus on changed behavior, regression risk, and missing tests. For full repository audits, it can go wider: architecture risks, dependency concerns, dead code, documentation gaps.

A GitHub-native implementation can use GitHub App authentication, `pull_request` webhooks, Checks API status reporting, review comments for line-specific findings, artifacts for full reports, and labels for severity or review state.

The agent should not block merges automatically unless the organization explicitly configures that behavior. Early versions are safer as advisory reviewers.

## Engineering Principles

The main design principle is evidence-first review. The agent reads, searches, runs, and verifies before it makes a claim.

- Prefer repository conventions over generic conventions.
- Keep generated fixes small and easy to review.
- Separate observation from inference.
- Cite files and commands for every important claim.
- Degrade gracefully when tests or dependencies cannot run.
- Avoid overwhelming maintainers with low-confidence findings.

Human review stays in charge. The agent's job is to make it faster, more systematic, and more precise.

<ArticleLanguage language="zh">

审查一个 GitHub 仓库是一次工程调查。要做出判断，得先弄清楚项目边界、运行方式、依赖关系、测试覆盖，以及哪些路径一旦出错会影响真实用户。

GitHub repo review agent 应该围绕这个过程来设计：能拉取或读取仓库，建立项目索引，执行本地验证，并把结论落到具体文件、命令和失败模式上。只会对代码片段发表评论的聊天机器人做不到这些。

## 系统目标

这个 agent 有三个目标：

- 建立对仓库结构的系统理解。
- 从大量代码里挑出真正有风险的信号。
- 输出维护者能立刻处理的 review finding。

正确性、安全性、可维护性和测试缺口要排在代码风格前面。一个好的 agent 应该能说清楚：这个接口接收用户输入，把数据传给某个 parser，再写入存储层，但当前没有测试覆盖异常输入。

## 架构设计

一个可落地的 review agent 可以拆成下面这条流水线：

```text
GitHub Repository
      |
      v
Repository Loader
      |
      v
Project Indexer
      |
      v
Static Analysis + Semantic Search
      |
      v
Test / Build / Lint Executor
      |
      v
Risk Scoring Engine
      |
      v
Review Report Generator
```

每个阶段只负责一类问题。拆开之后，agent 的行为更容易调试、度量，也更容易改进。

## 仓库加载

第一步是以可复现的方式加载仓库。agent 需要记录：

- GitHub URL、分支、commit SHA、PR 编号。
- 从 `package.json`、`pyproject.toml`、`go.mod`、`Cargo.toml`、`pom.xml`、`build.gradle` 等文件识别语言和框架。
- 从 `.github/workflows`、`circleci`、`buildkite` 等目录识别 CI 配置。
- 依赖锁文件，例如 `package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`、`poetry.lock`、`uv.lock`、`Cargo.lock`。

commit SHA 很关键，因为 review 必须可复现。finding 如果只指向一个不断变化的 branch，证据就会漂移，后续很难定位。

## 项目索引

仓库拉到本地之后，agent 建立项目索引。索引里既有结构信息，也有语义信息：

- 文件树，排除生成物和构建产物。
- 入口点：API routes、CLI commands、应用启动入口、worker、定时任务。
- 导出的函数、类、接口和模块。
- 文件之间的 import 和依赖关系。
- 测试文件与实现文件的对应关系。
- 配置文件和环境变量的使用情况。

小型项目用文件遍历加语言 parser 就够。代码库变大之后，混合索引更合适：

- 用 `ripgrep` 做快速词法搜索。
- 对支持的语言做 AST 解析。
- 用 embedding retrieval 处理语义查询。
- 抽取 import graph 或 call graph，辅助依赖推理。

agent 不需要把全部文件塞进模型上下文。围绕当前的 review 假设按需检索就够了。

## 静态分析层

静态分析层找的是需要人看一眼的风险模式，例如：

- 用户输入流向文件系统、SQL、shell、网络请求或反序列化 API。
- 认证或授权检查缺失、不一致。
- 过宽的 `catch` 逻辑吞掉真实错误。
- 不安全的 shell command 拼接。
- 缺少请求体大小限制。
- 存在竞态风险的更新流程。
- 并发代码中的共享可变状态。
- 没有上限的重试、分页、递归或队列消费。
- 误提交到源码里的 secret。
- 错误路径没有测试覆盖。

这一层最好把确定性规则和 LLM 推理结合起来。确定性规则擅长精确模式，LLM 擅长把多个文件串成一条行为路径。

## 本地验证执行

agent 能执行维护者平时会跑的命令，review 才真正有用：

```bash
npm test
npm run lint
npm run typecheck
pytest
go test ./...
cargo test
```

agent 应该从 package scripts、CI workflow 和 README 里推断验证命令。每跑一次，记录命令、exit code、耗时、关键失败输出，以及失败是否和当前 review 内容有关。

没跑过命令的 finding，说服力要弱一些。命令因为缺少服务、凭证或环境变量而失败，这条信息也该进报告。

## 风险评分

不是所有问题都值得同等关注。实用的 agent 会按风险给 finding 排序：

```text
risk = impact * likelihood * reachability * confidence
```

- Impact 表示问题发生后的损害程度。
- Likelihood 表示正常使用中触发这个问题的概率。
- Reachability 表示代码路径是否会被真实用户或自动化流程触达。
- Confidence 表示 agent 手上证据的强度。

排序之后，review 不至于变成长长的低价值意见列表。排在最前面的应该是可能造成数据丢失、安全暴露、生产事故、发布失败或重大回归的问题。

## Review 输出格式

有用的 finding 要短、具体，能落到证据上，维护者才好动手：

```text
Severity: High
File: src/api/import.ts
Issue: 上传文件在校验大小和 content-type 之前就被解析。
Why it matters: 大文件或畸形文件可能在被拒绝前造成过高内存占用。
Suggested fix: 在读取完整 body 之前先校验请求大小和 MIME 类型。
Verification: 增加超大文件、不支持 MIME 类型、畸形 payload 的测试。
Evidence: import route 在 validateUploadMetadata(req) 之前调用了 parseUpload(body)。
```

“加强校验”这样的建议没法执行。上面的格式会指出具体的失败模式，并给出证据所在的位置。

## GitHub 集成方式

常见的集成方式有两种：

- Pull request review mode：先看 diff，需要时再扩展到上下文文件。
- Repository audit mode：看整个仓库，输出架构和风险报告。

对于 PR，控制范围很重要。agent 应该关注行为变化、回归风险和测试缺口。全仓库 audit 则可以放宽范围，覆盖架构风险、依赖问题、死代码和文档缺口。

一个 GitHub 原生实现会用到 GitHub App authentication、`pull_request` webhook、Checks API 状态回写、行级 review comments、artifacts 和 labels。早期版本不要默认阻塞 merge，先当 advisory reviewer 更稳妥。

## 工程原则

最重要的原则是 evidence-first review：先读、先搜、先跑、先验证，再下结论。

- 优先遵循仓库自己的工程约定。
- 自动生成的修复要小，方便 review。
- 区分观察结果和推理结论。
- 重要结论要引用文件、代码路径或命令结果。
- 测试或依赖跑不起来时，说清楚限制。
- 别用低置信度的 finding 打扰维护者。

拍板的是人。agent 要做的是让 review 更快、更有条理、更精确。
