Using Codex feels different from autocomplete. It reads the project, edits files, runs checks, and keeps going while I think about what the page should be. The closest thing is a coding partner who is fast and needs direction.

Raw speed is easy to measure. The feedback loop matters more: describe the change, inspect the result, adjust the details, verify, repeat.

## How I work with it

My starting point is usually a rough intention, not a specification. Something like: the blog section feels repetitive, this button is not obvious enough, or the homepage still does not feel professional.

Codex turns that into implementation steps: read the code, find the files that matter, edit the UI, run lint and the build, and preview the page locally.

## What it is good at

The repetitive work is where it earns its place. Updating copy, adding a route, wiring MDX posts into a registry, adjusting Tailwind classes, running the verification commands afterwards: none of it is hard, all of it takes time, and Codex does not lose the thread in the middle.

It is also good at turning the repo into writing. Listing the technologies is the easy version. Codex can pull out the architecture, the trade-offs, and the parts worth explaining.

## Where I still lead

The decisions that matter are still mine: what is true, what belongs on a public page, which projects are finished enough to feature, whether the tone sounds like me.

Design judgment works the same way. Codex will propose a layout, and I still have to look at it and decide that the page is too crowded, too repetitive, or too generic.

## Notes

- An agent that can inspect the real codebase beats one that has to guess from a vague description.
- Fast iteration only counts when lint, the build, and a local preview confirm the result.
- Collaboration means giving direction, reading the output, and pulling the agent back when the product story drifts.
- AI can accelerate implementation. Taste, accuracy, and authenticity stay with the developer.
- A portfolio built with an agent should still read like the person it belongs to.

## Takeaway

Codex helps me move faster, and it takes over a lot of implementation detail. The judgment stays mine: what to show, what is true, and whether the page sounds like me. Those calls are what keep the work honest and useful.

<ArticleLanguage language="zh">

用 Codex 和用普通的代码补全不是一回事。它会读项目、改文件、跑检查，我主要负责想清楚页面该是什么样、接下来往哪走。更接近的说法是，有一个手很快、但需要你给方向的编程搭档。

快当然好，但真正有用的是那个反馈循环：说清要改什么，看结果，调细节，验证，再来一轮。

## 我的用法

我一般从一句粗糙的想法开始，而不是先写一份完整需求。比如“博客这块看着太重复”“这个按钮不够显眼”“首页整体还不够专业”。

Codex 会把它拆成具体动作：读代码、找到相关文件、改 UI、跑 lint 和 build，再在本地把页面跑起来看效果。

## 它擅长什么

重复性的工程活是它的强项。改文案、加路由、把 MDX 文章接进 registry、调 Tailwind 类名、改完再跑一遍验证命令，这些事不难，但很占时间，它做的时候不会把上下文弄丢。

它也很适合把仓库变成文章。只列技术栈是最省事的写法，它能从代码里把架构、取舍和值得讲的点梳理出来。

## 哪些还得我来

判断上的事还是得自己做：什么是真的、什么适合公开、哪些项目已经完整到可以放上来、这个语气像不像我。

设计判断也一样。Codex 能给出布局方案，但页面是不是太挤、太重复、太像模板，还是得我看了之后决定。

## 几点体会

- agent 能看到真实代码库时，效果好很多；只给它一段模糊描述，它只能猜。
- 迭代快本身没有意义，lint、build、本地预览都过了才算数。
- 协作的关键是给方向、看输出，发现产品叙事跑偏时及时拽回来。
- AI 能加速实现，但品味、准确性和真实感还是开发者自己的事。
- 用 agent 做出来的作品集，读起来也该像作者本人写的，而不是自动生成的。

## 收尾

Codex 确实让我快了不少，很多实现细节它也接了过去。剩下的是判断：展示什么、什么是真的、读起来像不像我。这些判断才决定最后做出来的东西诚不诚实、有没有用。
