I built this simulator to work through four things at once: reliable messaging, heartbeats as a liveness signal, authentication, and peer-to-peer file sharing.

The design puts control and bulk data on different protocols. UDP carries authentication, commands, and heartbeats. TCP carries file payloads, and only between peers.

## Highlights

- UDP control plane for auth, commands, heartbeat messages, and peer discovery.
- TCP data plane for streaming file payloads from publishers.
- Heartbeat pruning removes inactive peers after the timeout.
- Server state tracks address-to-user mappings, active timestamps, and published file metadata.
- Each client binds a TCP server to an ephemeral port and advertises that port when it publishes a file.

## Server State

The server keeps four maps: address to username, username to address, client activity timestamps, and file ownership. With those it can authenticate a command, list who is online, and tell a client where to find a file.

The server does not host files. It runs closer to a directory service: once the client has the publisher address, the download goes over TCP directly between the two peers.

## Commands

- `pub <file>` publishes a local file if it exists.
- `get <file>` asks the server for the publisher address, then opens TCP to fetch the file.
- `lap` and `lpf` list active peers and published files.
- `sch <substr>` searches published files across peers.
- `unp <file>` unpublishes a file for the current user.

## Notes

It started as a lab simulator. The obvious extensions are TLS, per-chunk checksums, retry backoff, and richer observability.

## Knowledge Points

- UDP is useful for lightweight control messages, but liveness and identity have to be built in the application.
- TCP fits file transfer because it gives an ordered, reliable byte stream.
- A heartbeat turns silence into a failure you can detect.
- A directory server pattern coordinates peers without proxying every file payload.
- The client needs threads: it has to accept TCP downloads while it keeps sending UDP commands.
- Protocol commands need validation and clear error responses, or the client cannot tell what happened.
- A production version would add stronger auth, encryption, retries, and checksums.

<ArticleLanguage language="zh">

我写这个模拟器，是想一次把四件事走通：可靠消息传递、用心跳判断节点是否还活着、身份认证，以及点对点文件共享。

控制面和数据面放在了不同的协议上。UDP 负责认证、命令和心跳；TCP 只负责文件数据，而且只在节点之间传。

## 亮点

- UDP 控制平面处理认证、命令、心跳消息和节点发现。
- TCP 数据平面从发布者那里流式传输文件。
- 心跳清理会在超时后移除不活跃的节点。
- 服务器状态记录地址到用户名的映射、活跃时间戳和已发布文件的元数据。
- 每个客户端绑一个临时端口的 TCP server，发布文件时把这个端口公布出去。

## 服务器状态

服务器维护四张映射：地址到用户名、用户名到地址、客户端活跃时间戳、文件归属。有了这些，它能校验命令、列出在线节点，并在文件请求时告诉客户端去哪里取。

服务器本身不存文件，更接近一个目录服务。客户端拿到发布者地址以后，TCP 连接直接在两台机器之间建立。

## 命令

- `pub <file>` 发布本地文件，文件不存在就失败。
- `get <file>` 向服务器要发布者地址，然后开 TCP 连接取文件。
- `lap` 和 `lpf` 分别列出活跃节点和已发布文件。
- `sch <substr>` 在所有节点的已发布文件里搜索。
- `unp <file>` 取消当前用户的文件发布。

## 备注

最初是当实验室模拟器写的。往下可以加的东西很清楚：TLS、分块校验和、重试退避，以及更细的运行状态观察。

## 知识点

- UDP 适合轻量的控制消息，但活跃性和身份都得在应用层自己实现。
- TCP 适合传文件，因为它给的是有序、可靠的字节流。
- 心跳把"没声音"变成了一个可以检测的故障。
- 目录服务模式能协调节点，又不用代理每一份文件数据。
- 客户端需要多线程：一边接受 TCP 下载，一边还要发 UDP 命令。
- 协议命令要检查输入，并给出明确的错误响应，否则客户端不知道自己错在哪。
- 真要做成产品，还得加认证加固、加密、重试和完整性校验。
