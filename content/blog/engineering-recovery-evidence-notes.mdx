Across the existing AgentScope notes, the Sidecar harness, and this portfolio rebuild, one question keeps coming back: after an interruption, what can a user safely understand and do? These notes are about design, not measured performance.

## Persist what changes the next decision

A useful checkpoint holds enough state to choose the next safe action. A transcript alone may not say whether a tool already changed the outside world. Sidecar's intent journal exists because an uncertain side effect needs its own state.

For a form, the analogous state is the saved answer and the step that can be resumed. For an agent, it may also include an approval boundary and a pending external result. What gets stored should follow from the recovery question.

## Match the interface to the evidence

"Working", "waiting for you", and "verified" should be different interface states. A polished activity animation should not imply progress the system cannot substantiate.

The same distinction applies to a website audit. Compressed asset size can be measured locally; a claim about real-user LCP requires field data. A successful build verifies compilation, not every keyboard or language interaction.

## Reduce hidden work

The previous version delayed navigation to play a fade, and the bilingual articles rendered both languages and hid one with CSS. Both did work the reader did not ask for.

The rebuild navigates immediately, adds a keyboard skip link, selects article language on the server, and moves motion below the first screen. The aim is for the next useful action to arrive sooner and to stay understandable.

## Review failure paths as part of the product

A practical review asks four questions: what survives a restart, which effects are uncertain, what evidence supports success, and what the user can do next. These questions apply to backend services, agent tools, and interfaces because interruption is a normal operating condition.

从已有的 AgentScope 笔记、Sidecar 执行核心，到这次个人站改造，一个问题反复出现：中断之后，用户能可靠地理解什么、继续做什么？下面写的是设计判断，没有性能数据。

## 保存能改变下一步决策的状态

有用的检查点要包含足够的状态，让人能判断下一步做什么是安全的。聊天记录可能没有说明工具是否已经改变外部环境。Sidecar 的动作意图日志说明，不确定的副作用需要单独的状态。

对于表单，对应的状态是已保存的答案和可以恢复到的步骤；对于 Agent，还可能包括审批边界和等待中的外部结果。该存什么，取决于恢复时需要回答什么。

## 界面表达要匹配证据

“正在处理”“等待你介入”和“已验证”应该是不同状态。再好看的加载动画，也不能暗示系统无法证明的进展。

网站评审也是同一个道理：压缩后的文件大小可以本地测量，真实用户 LCP 则需要线上实测数据。构建成功证明编译通过，不等于所有键盘和语言交互都正确。

## 减少隐形工作

旧版本会先播一段淡出动画再跳转页面；双语文章也会同时渲染两种语言，然后用 CSS 隐藏其中一种。这两件事都是读者没要求的工作。

这次改成了直接导航、键盘跳转入口、服务端选择文章语言，动效放在首屏以下。目标是让下一步有效操作更早出现，也更容易理解。

## 把失败路径纳入产品评审

一次实用的评审要问四个问题：重启后什么还在、哪些副作用不确定、什么证据支持完成、用户接下来能做什么。后端服务、Agent 工具和界面都适用，因为中断本来就是正常运行条件。
