<ArticleLanguage language="en">

The Anchor program is the part people ask about. The rest of the system is about what happens after a transaction lands.

Solana OrderFlow has two halves. On chain, an Anchor program owns the escrow state and the tokens. Off chain, services read the program logs, normalize them, publish to Kafka, write Postgres, and run the consumer workflows.

## On-Chain Layer

Three instructions cover the flow: create an offer, take an offer, cancel an offer. Creating one moves tokens into a vault token account tied to that offer. Filling or canceling empties that vault, and the program authorizes the transfer with PDA signer seeds instead of a private key.

The escrow account holds the maker address, the mint accounts, the requested amount, the offered amount, the status, and the bump. Status is Created, Filled, or Cancelled, and the transition is explicit, which matters in a flow that moves money.

## Off-Chain Pipeline

The listener opens a WebSocket subscription to program logs, turns each JSON-like message into an event record, and publishes it to Kafka. A storage writer consumes the events and writes two tables: an append-only event table and an offer snapshot table.

The split earns its keep. Events keep history; the snapshot keeps queries cheap. The writer also uses idempotent keys and commits Kafka offsets by hand, so a failed database write leaves the event available for retry instead of dropping it or counting it twice.

## Risk and Notification

The risk engine reads the same stream and applies rules. Large offer amounts and repeated cancels are the two it starts with. Alerts go to their own topic, so notification code can change without touching detection.

## Knowledge Points

- An escrow program is easier to review when custody and state transitions are explicit.
- PDA signer seeds let a program move tokens out of accounts it owns without holding a private key.
- Program logs are the practical bridge between on-chain execution and off-chain indexing.
- Partition keys, idempotent producers, and manual commits are the parts of a Kafka pipeline that decide whether it stays correct under retries.
- Append-only events plus snapshot tables are the usual event-sourcing shape behind a dashboard.
- Amounts crossing a language boundary need care, because a JavaScript number cannot hold every token amount exactly.
- A risk engine can start with rules and move to scoring later.

## Takeaway

The contract is one layer. Ingestion, storage, idempotency, monitoring, and downstream consumers are the rest, and each of them can fail on its own.

<ArticleLanguage language="zh">

Anchor 程序是大家最先问到的部分。交易上链之后发生的事，占了另外一半。

Solana OrderFlow 分成两半。链上是 Anchor 程序，持有托管状态和代币；链下是一组服务，监听程序日志、整理成事件、发到 Kafka、写入 Postgres，再各自跑消费者逻辑。

## 链上层

三条指令撑起主流程：创建 Offer、接受 Offer、取消 Offer。创建时，代币进入与该 Offer 关联的 vault token account。成交或取消时，程序用 PDA signer seeds 授权把代币转出，这个账户本身没有私钥。

托管账户里存 maker、mint 账户、请求数量、提供数量、状态和 bump。状态取 Created、Filled、Cancelled，状态转换是显式的；钱在动的流程里，状态必须一眼能看懂。

## 链下流水线

监听器通过 WebSocket 订阅程序日志，把每条类似 JSON 的消息整理成事件记录，发到 Kafka。存储写入器消费这些事件，写两张表：仅追加的事件表和 Offer 快照表。

这样拆开是有用的。事件表留着历史，快照表让查询不用扫全表。写入器还用幂等键和手动提交 offset，数据库写失败时事件还在，可以重放，不会静默丢失，也不会重复计数。

## 风险与通知

风险引擎读同一条流，按规则做检查，比如金额特别大的 Offer、短时间内反复取消。告警写到单独的 topic，通知逻辑改起来不用碰检测逻辑。

## 知识点

- escrow 流程里，代币托管和状态转换写得越显式，越容易审。
- PDA signer seeds 让程序在没有私钥的情况下，从自己拥有的账户转出代币。
- 程序日志是链上执行和链下索引之间最实际的一层桥。
- Kafka 流水线在重试下还对不对，取决于 partition key、幂等 producer 和手动提交这几处。
- 仅追加事件加快照表，是仪表盘类需求里常见的事件溯源做法。
- 金额跨语言传递要小心，JavaScript 的 number 装不下所有代币金额。
- 风险引擎可以先从规则写起，之后再换成评分模型。

## 总结

合约只是其中一层。数据摄取、存储、幂等、监控和下游消费者是其余部分，每一层都能单独出问题。
